The Event Loop

JavaScript can only do one thing at a time. So how does it handle clicks, timers, and network calls all at once without freezing? One chef, many helpers, and a tray of tickets.

one thread helpers ticket queue
1

One chef, one pan

JavaScript has a single thread: one call stack, one job at a time. Every click, timer, and response becomes a ticket waiting its turn.

2

The problem: slow orders

If the chef personally waits for a slow job, the whole kitchen stops. No clicks, no scrolling, no other tickets — the page (or server) is frozen.

3

The trick: hand it off

The chef never waits. Slow work goes to helpers — the browser's Web APIs, or Node's libuv and the operating system. When a helper finishes, it drops a ticket (your callback) into the queue. The event loop is just a rule: when the stack is empty, run the next ticket.

4

Promises jump the line

There are actually two queues. Promise callbacks (.then, await) go in a VIP microtask queue that is emptied completely before the next regular ticket. That's why a promise beats a setTimeout(…, 0).

console.log("1");                              // sync — right now
setTimeout(() => console.log("4"), 0);        // regular queue
Promise.resolve().then(() => console.log("3")); // VIP queue
console.log("2");                              // sync — right now

// prints: 1  2  3  4 — the promise beats the "0 ms" timer
5

Node.js: same loop, different helpers

Node.js is the same engine (V8) and the same loop, taken out of the browser and given server helpers. That's the whole difference.

6

If you remember one thing

Never block the loop.

  • One thread — a slow synchronous job freezes everything.
  • Hand slow work to helpers with async APIs; take the result as a callback ticket.
  • Promises are VIP tickets — they run before any setTimeout, even a 0 ms one.
