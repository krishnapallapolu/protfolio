The Toy Box Rule

One database. Many companies' rows, all in the same tables. How does Org A never, ever see Org B's stuff — even when the code asks badly?

A polite sign is not a lock

Without RLS, the only thing keeping rows apart is your app remembering to say WHERE organizationId = … on every single query. Forget it once, and…

Make the box do the checking

RLS gives every row a name tag and makes each transaction wear a wristband first. The database itself only hands over rows whose tag matches the band — even when the query asks for everything.

The catch: the janitor's master key

Whoever owns the tables skips the checks entirely. So the app must connect as an ordinary member — never as the owner.

The box's own rule
CREATE POLICY … USING ("organizationId" = current_setting('app.current_org', true))
No faking tags on the way in
WITH CHECK — the same match runs on INSERT and UPDATE
No band → empty box
an unset setting is NULL, which matches no row — the system fails closed, never open
The janitor's master key
the table-owner role bypasses non-FORCE policies — so the app connects as app_user, and the owner connection stays for migrations

The whole thing in one breath

Every row carries its org. Every transaction declares its org. The database itself filters every read and write to that org, returns nothing when no org was declared, and enforces all of it for any role except the table owner — which is exactly why the app never connects as the owner.

Why SET LOCAL and not SET? Because it lives and dies with one transaction. Through a transaction-mode pooler like pgbouncer, the wristband and the query are guaranteed to share the same backend connection — so the lane can never leak onto someone else's borrowed connection.
